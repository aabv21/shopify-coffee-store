# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

This repo builds the order-processing backend for Nubandina Coffee, a fictional Shopify coffee store, as an n8n workflow backed by Postgres, plus the storefront theme. It is a portfolio demo: every file should read as production-quality, not a prototype.

## Repo map

- `compose.yaml`, `.env.example` — the local runtime: Postgres and n8n in Docker Compose, plus an optional ngrok tunnel (profile `tunnel`).
- `compose.queue.yaml` — an optional override that adds Redis and `n8n-worker` containers for queue mode; see Commands.
- `db/schema.sql`, `db/init/` — the application database's baseline schema (table `orders`) and the one-time role/database bootstrap script, both run only on an empty volume. `db/migrations/` — every schema change after that baseline, as an idempotent, numbered `NNN_short_name.sql` file that `pnpm run db:migrate` applies once each: `001_runtime_role.sql` creates the least-privilege `app_runtime` role and grants it exactly what `intake-order`'s one Postgres statement needs. `docs/database.md` covers the roles, every statement and its grant, migrations, retention, backup and restore, connections, the upgrade path for an existing local volume, and what `check-db` proves.
- `ngrok/traffic-policy.yml` — the tunnel's traffic policy: forwards only the Shopify Trigger's own fixed webhook path, denying every other path, including other webhook-shaped ones.
- `config/config.example.json` — the config template; a developer's own `config/config.json` is gitignored. `src/lib/config.ts` holds `validateConfig`, the pure validator both `scripts/check-config.ts` and `scripts/setup.ts` run against it — see Commands.
- `data/products.csv` — the Shopify product import CSV: 3 coffee origins (Nariño, Huila, Sierra Nevada) in 250 g and 500 g, with the `coffee` namespace metafields (roast, tasting notes, brew method). Header spelling and value formats (`Active`, `TRUE`/`FALSE`, `DENY`) come from Shopify's public sample CSV, not a store download — there is no store yet. `data/brewing-guides.json` — one brewing guide per brew method (pour-over, espresso, french press), mounted read-only into n8n at `/files/data/brewing-guides.json` for `process-order`'s brewing-guide email. Because the mount is read-only and live, an edit to a guide's text or steps takes effect on the next execution that reaches "Read brewing guides" — no re-import, no restart.
- `docs/shopify-setup.md` — the owner's step-by-step guide for creating the dev store and importing the catalog: metafield definitions, currency format, the CSV import, shipping rates, the test payment gateway, and the product image credits. Manual; nothing in this repo runs it.
- `docs/architecture.md` — how the system works: components, the order flow, the data model, failure modes, scaling, security, and design decisions. `docs/diagrams/` — the archify JSON sources (`architecture.json`, `order-sequence.json`) and, for each one, its interactive HTML page and exported SVG; see "Regenerate a diagram" under Commands.
- `workflows/` — the n8n workflow JSON, mounted read-only into n8n. In place: `load-config` (reads and returns `/files/config/config.json`, unvalidated, failing loudly instead of silently when it's missing; it names no error workflow, because `error-handler` calls it and one would loop), `error-handler` (the shared error workflow: loads config, emails the owner a plain-text alert — this also covers a trigger that fails at startup, such as a revoked credential, which carries no `execution` data), `dev-harness` (a token-protected, localhost-only webhook for calling a sub-workflow directly; see Commands), `shopify-orders` (the thin entry point: the Shopify Trigger itself, plus a handoff to `intake-order` — see "The intake split" below), `intake-order` (normalizes the order, records it once, and hands it to `process-order`), and `process-order` (the core order workflow, entered through its own Execute Workflow Trigger with the input contract `{ order: NormalizedOrder, config: Config }`: builds one flat sheet row, upserts it into the configured Orders tab keyed by order number, emails the owner a plain-text summary, reads the ordered variants' stock and brew method from Shopify's GraphQL Admin API and emails the owner a separate alert naming whichever variants fell below `config.low_stock_threshold`, then — after either low-stock branch — waits `config.guide_delay_minutes` minutes and emails the customer an HTML brewing guide for whichever brew methods its order matched, skipping silently when there's no address or no known method).
- `scripts/lib/manifest.ts` — the single source of truth for fixed workflow/credential/code-node IDs (`WORKFLOWS`, `CREDENTIALS`, `CODE_NODES`, `TRIGGER_WEBHOOK_ID`); a `WORKFLOWS` entry's optional `webhookPath` names its live webhook path, for `import-workflows.ts`'s post-publish liveness poll (see "Changing a workflow" below) — set today only for `dev-harness` (`dev`), never for `shopify-orders`, whose trigger path must never be probed (see the tunnel guardrail below). `scripts/lib/` also holds the workflow types, `normalizeWorkflow`, `listJsonFiles`, the Docker Compose and `.env` helpers (`compose.ts`, including stdin support for streaming data into a container), the `/healthz` and webhook-liveness polls (`health.ts`), and the dev-harness client (`dev-client.ts`).
- `scripts/check-workflows.ts`, `scripts/build-workflows.ts`, `scripts/export-workflows.ts`, `scripts/import-workflows.ts`, `scripts/setup-credentials.ts`, `scripts/setup.ts`, `scripts/dev-call.ts`, `scripts/send-test-order.ts` — the workflow tooling CLIs; `scripts/check-config.ts` and `scripts/shopify-token.ts` — the config check and the Shopify token CLIs; `scripts/init-env.ts` — writes `.env` from `.env.example` with generated secrets, for everyone — CI has no repo secrets to fill it by hand, and the quick start runs the same script locally; `scripts/check-dev-response.ts` — CI's proof that n8n actually executes a workflow (see "The `n8n` job" under Supply-chain hardening below); `scripts/assemble-theme.ts`, `scripts/build-theme.ts`, `scripts/theme-check.ts`, `scripts/lib/horizon.ts`, and `scripts/lib/theme-insertions.ts` — the theme toolchain. See Commands below.
- `src/nodes/` — Code-node sources for workflows (added with the workflows that need them). `src/theme/` — pure TypeScript modules behind the storefront theme. `src/globals.d.ts` declares the ambient `DateTime` global the n8n Code-node sandbox provides.
- `theme/` — this repo's own overlay onto Shopify's Horizon theme: new theme files plus `README.md`, which documents the overlay and insertions model and is itself never shipped. See "The theme toolchain" below.
- `tests/` — Vitest tests; `tests/setup.ts` provides the `DateTime` global at test time, matching the sandbox. `tests/lib/code-node.ts` runs a generated Code node's `jsCode` the way n8n's real Task Runner sandbox does (`Object.defineProperty` replaced with a no-op before the code runs). `tests/fixtures/workflows/` holds the hygiene-check fixtures: `clean.json` is a valid workflow, each other file is `clean.json` plus one defect. `tests/fixtures/orders/` holds raw `orders/create` payload fixtures (`tests/lib/orders.ts`'s `fx` loads them), covering a normal order, free shipping, a guest with no email or addresses, two shipping methods, and low stock. `tests/fixtures/theme-base/` and `tests/fixtures/theme/` hold the theme-toolchain fixtures: a tiny theme (one snippet, one settings schema, one JSON template) standing in for Horizon, and a one-line TypeScript module standing in for a theme asset's source.
- `tsconfig.json`, `eslint.config.ts`, `vitest.config.ts`, `package.json` — the TypeScript toolchain.
- `.n8n-import/` — created locally by `node scripts/init-env.ts`; a scratch directory `export-workflows.ts` writes n8n's `export:workflow` output to (`.n8n-import/export`) — `import:workflow` itself reads from the separate `./workflows:/workflows` mount, not this directory. No credential data crosses it at all: `setup-credentials.ts` streams the decrypted import JSON into the `n8n` container over stdin, and reads back the existing-credentials export (still encrypted — ids, names, types, and encrypted data, of which only the ids are used) over stdout — both travel entirely inside the container's own `/tmp`, never through this bind mount (see that script's own comments on `IMPORT_SCRIPT` and `EXPORT_SCRIPT`). It's a live bind mount: never `rm -rf` it; the tooling only ever deletes the specific files it writes there. On Linux, it works only when the host uid matches n8n's container uid (1000), because n8n writes into a directory the host creates at 0700.
- `.theme-build/` — created locally by the theme toolchain; gitignored. Holds the downloaded, extracted Horizon commit (`horizon-<commit>/`, reused across runs instead of re-downloading) and the assembled, pushable theme (`theme/`). Safe to delete; the next `theme:assemble` or `theme:check` rebuilds it.
- `.github/workflows/`, `.github/dependabot.yml` — CI (quality, security, actions-lint, and `n8n` jobs; CodeQL once the repo is public) and automated dependency updates. The `n8n` job boots the real stack and proves a workflow executes end to end; see "The `n8n` job" under Supply-chain hardening below.

## Commands

- `pnpm install --frozen-lockfile` — install dependencies from the lockfile.
- `pnpm run typecheck` — `tsc --noEmit`.
- `pnpm run lint` — `eslint .`.
- `pnpm test` — `vitest run`.
- `docker compose ls` — list running Compose stacks; run this before starting the stack, since every demo in this series binds `127.0.0.1:5678`. Stop any other demo's stack first.
- `docker compose up -d --wait` — start Postgres and n8n, and wait for both to report healthy.
- `docker compose --profile tunnel up -d --wait` — also start the ngrok tunnel (needs `NGROK_AUTHTOKEN` and `NGROK_DOMAIN`).
- `docker compose down` — stop the stack. Add `-v` to also drop the named volumes (destructive: wipes the database and n8n's data).
- `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` — switch to queue mode: adds Redis and the given number of `n8n-worker` containers, which run executions instead of the main process. `n8n-worker` extends `compose.yaml`'s own `n8n` service (same encryption key, database settings, and read-only `/files` mounts), with its published port reset so it scales past one replica without a conflict.
- `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — return to the regular, single-process stack. Plain `down`, with no `-v`, keeps the named volumes.
- `pnpm run build:workflows` — bundles each `src/nodes/*.ts` Code node with esbuild into its node's `jsCode`, and sets its `notes` to `Why Code: <why>`. Add `-- --check` to fail (exit 1) if the committed JSON doesn't match the source, without writing — that's what CI runs.
- `pnpm run check` — hygiene checks on every file in `workflows/`: pinned data, `meta.instanceId`, required settings (including `errorWorkflow: nbcErrorHandler1` on every workflow except `error-handler` and `load-config`), a literal email/phone/long-id/secret, an unknown credential id, a hand-written or undocumented Code node, an external-service node without the required retry, a Postgres query built from an expression instead of `$n` parameters, a Postgres query with a `$n` placeholder inside a SQL comment, and a missing sticky note. `node scripts/check-workflows.ts <dir>` runs it against any directory and prints `<file>: <message>` per violation.
- `pnpm run check:config` — runs `validateConfig` (`src/lib/config.ts`) against `config/config.json` and prints `config OK`, or the first validation error with a non-zero exit.
- `pnpm run db:migrate` — applies every pending file in `db/migrations/` (`scripts/db-migrate.ts`), each in one transaction with its `schema_migrations` row, as the Postgres superuser over the `postgres` container's local socket, then sets `app_runtime`'s password from `APP_RUNTIME_DB_PASSWORD` and re-asserts its attributes (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), with `log_min_error_statement` raised to `panic` for that transaction so a failed `ALTER ROLE` never logs its password. Each file's transaction takes a fixed advisory lock first. Stops before touching the database when a file contains a transaction-control statement, when `APP_RUNTIME_DB_USER` shares its name with another role variable, or when a variable a pending file reads with `\getenv` is unset or empty, naming files and variables only. A second run prints `no pending migrations`. See `docs/database.md`.
- `pnpm run setup` — runs `db:migrate` first, then validates `config/config.json` (same check as `check:config`), then imports credentials (`scripts/setup-credentials.ts`) and publishes workflows (`scripts/import-workflows.ts`) into the local n8n instance, in that order (`node scripts/setup.ts`, not `a && b`, so `-- --live`/`-- --refresh <id>` flags reach both later steps). Skips a credential whose `.env` values are blank, or one that already exists unless named with `--refresh <id>` (any number of times) — re-importing a credential replaces it, which would otherwise drop an interactive Google sign-in (the `App DB` credential has none, but the same skip rule still applies to it; see `docs/database.md`'s upgrade path for the one-time refresh an existing stack needs). Skips a workflow not yet in `workflows/`. **A `liveTrigger` workflow (`shopify-orders.json` today) is only published with `--live`** — `pnpm run setup` on its own leaves the Shopify trigger unpublished, so running it again after a live publish (for example, to refresh a credential) takes the store's live order intake offline unless `--live` is passed again.
- `pnpm run export` — writes n8n's canonical form of every known workflow back to `workflows/` and regenerates their Code nodes; run this after editing a workflow in the n8n UI, and commit the result.
- `node scripts/dev-call.ts <target> '<json>'` — calls the dev-harness webhook (`POST {N8N_URL}/webhook/dev`) directly, for exercising a sub-workflow offline, without a real Shopify order. For example, `node scripts/dev-call.ts load-config '{}'` returns `{ "config": { ... } }` read straight from the mounted file. `node scripts/dev-call.ts intake-order "$(cat tests/fixtures/orders/below-threshold.json)"` runs the whole intake chain against a fixture order: the harness shapes the raw payload into one item the same way the Shopify Trigger would emit it, then calls `intake-order` directly, bypassing the HMAC check entirely (that's the point — it's for exercising the chain behind the trigger, not the trigger itself; `scripts/send-test-order.ts` drives the real, signed path). Needs `DEV_HARNESS_TOKEN` in `.env` (never printed). An unknown target answers 404. The harness has two targets, `load-config` and `intake-order`. See Guardrails below for the harness's own workflow, `dev-harness.json`.
- `pnpm run shopify:token [-- --client-credentials]` — gets the Admin API access token for n8n's Shopify credential (`docs/shopify-setup.md` "Admin API access"). By default it runs Shopify's authorization code grant: it prints an authorize URL, reads the resulting callback URL from stdin, and exchanges the code for an offline token that doesn't expire. `--client-credentials` is the fallback for a same-organization dev store: a token that expires in 24 h, which then needs `pnpm run shopify:token -- --client-credentials` and `pnpm run setup -- --refresh nbcCredShopify01 --live` re-run daily (the `--live` matters; see `pnpm run setup` above). Either way it writes `SHOPIFY_ACCESS_TOKEN` into `.env`, keeping the file at mode 0600.
- `pnpm run send-test-order [-- --fixture <name>] [--order-id <digits>] [--tamper]` — signs a fixture order from `tests/fixtures/orders/` exactly as Shopify signs a real `orders/create` webhook (HMAC-SHA256 of the raw body, base64) and posts it to the local Shopify Trigger's real, fixed webhook path, reading `N8N_URL`, `SHOPIFY_STORE`, and `SHOPIFY_CLIENT_SECRET` from `.env` (never printed). `--fixture` defaults to `below-threshold`; `--order-id` defaults to the current timestamp. `--tamper` mutates the body after signing it, so the signature no longer matches — this drives the real, HMAC-checked entry point (`shopify-orders`), unlike the dev harness, which bypasses it. Needs `shopify-orders` published with `--live` to do anything useful; see "Live checks (pending)" in the README.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` CLI commands need no owner account, `--userId`, or `--projectId` (checked against `2.45.6`). `publish:workflow` only takes effect after an n8n restart; `pnpm run setup` restarts n8n itself, but only when it actually published something, then waits for `/healthz`, then 15 s more for the publication reconciler, then polls each published workflow's own webhook (today, only `dev-harness`'s, by its manifest `webhookPath`) until it stops answering 404 — see "Changing a workflow" below.
- `node scripts/init-env.ts` — writes `.env` from `.env.example`, filling only the names the local stack and the dev harness need a real value for (`POSTGRES_PASSWORD`, `N8N_DB_PASSWORD`, `APP_DB_PASSWORD`, `APP_RUNTIME_DB_PASSWORD`, `N8N_ENCRYPTION_KEY`, `DEV_HARNESS_TOKEN`) with random hex, and leaving every other blank value (ngrok, Shopify, Google OAuth) untouched. Refuses to run if `.env` already exists. The quick start runs this for everyone, not just CI — CI has no repo secrets to fill the file by hand, but a local run gets the same generated local-stack secrets with nothing extra to do.
- `node scripts/check-db.ts` — runs psql inside the `postgres` container and prints `ok` or `FAIL` per check, exiting 1 on any failure: as `app_runtime`, `CREATE TABLE`, `DROP` and `TRUNCATE` on `orders`, connecting to the `n8n` database, and `SET ROLE` to the owner are all denied with the exact expected error; as the superuser, `app_runtime` holds no role attribute, no membership, no column-level grant beyond its table grant, and no `TEMP` on `app`; `app_runtime`'s privileges on every table and sequence in `public` equal `RUNTIME_GRANTS`, none missing and none extra; `intake-order`'s one Postgres statement runs as `app_runtime`, read straight from the workflow JSON, with `PROBES` binding its `$n` values, inside a transaction it rolls back; and `schema_migrations` records every file in `db/migrations/`. Each check's predicate is unit-tested in `tests/scripts/check-db.test.ts`, and a test fails when a new Postgres node has no probe. See `docs/database.md`.
- `node scripts/check-dev-response.ts [--fresh]` — first refuses to run at all, naming why, if a Google, Gmail, or Shopify credential already exists in n8n (see Guardrails below); otherwise calls the dev harness's `load-config` and `intake-order` targets (the fixture `tests/fixtures/orders/below-threshold.json`) and asserts each response against its known shape, exiting 1 (with the mismatched response printed) on anything else. Without `--fresh`, `intake-order`'s response may be either the fresh-call shape or, on a stack that already recorded this fixture's order, the duplicate-gate shape — right for a local re-run. With `--fresh`, only the fresh-call shape passes: this is what CI runs, since CI always starts from an empty database, so a bug that made every order read as a duplicate (for example, `Record order` silently stopping returning its row) would otherwise still pass on CI's own fresh database (`checksFor({ fresh })` holds the predicate-selection logic, unit-tested on its own). The `intake-order` path reaches `Normalize order` and `Check config`, two *generated* Code nodes, and the app Postgres (as `app_runtime`) through `Record order`, with no third-party credential needed. This is CI's `n8n` job proof that n8n actually executes the published workflow chain, not just that the webhook answers something.
- `pnpm run theme:assemble` — downloads the pinned Horizon commit (reusing a prior download), overlays `theme/**` onto it, applies the insertions in `scripts/lib/theme-insertions.ts`'s `INSERTIONS`, and writes the result to `.theme-build/theme/`; prints the added and modified file lists. See "The theme toolchain" below.
- `pnpm run build:theme [-- --check]` — bundles each entry in `scripts/build-theme.ts`'s `THEME_ENTRIES` with esbuild into `theme/assets/<asset>`, not minified (Shopify serves theme assets minified at request time). `--check` reports drift and exits 1 instead of writing — that's what CI runs.
- `pnpm run theme:check` — assembles the theme, then runs Shopify's theme check (`@shopify/theme-check-node`) against it; prints the failing offenses and a baseline count, and exits 1 on any failure. See "The theme toolchain" below for what counts as failing.
- Regenerate a diagram after you edit its source in `docs/diagrams/`. The diagram tool is [archify](https://github.com/tt-a1i/archify), which runs on Node.js with no install step; these sources were last checked against v3.2.0.

  Clone it outside this repo, so `pnpm run lint` never scans its files: `git clone --depth 1 --branch v3.2.0 https://github.com/tt-a1i/archify ../archify`. Run the commands from the repo root, because each source's `meta.output` path is relative to it. For the architecture diagram, whose source has type `architecture`:
  1. `node ../archify/archify/bin/archify.mjs validate architecture docs/diagrams/architecture.json --quality showcase --json`, after every edit, until it reports all 9 artifact checks passing with 0 composition errors and 0 warnings.
  2. `node ../archify/archify/bin/archify.mjs deliver architecture docs/diagrams/architecture.json docs/diagrams/architecture.html --quality showcase --json` writes the page. It also writes `docs/diagrams/architecture.delivery.json`, a receipt holding local absolute paths; git ignores it, so never force-add it.
  3. Open the page in a browser, choose **Export**, then **SVG · Auto**, and save the download over `docs/diagrams/architecture.svg`, which `README.md` and `docs/architecture.md` embed. The Auto variant follows the reader's light or dark theme.
  4. Optionally, `node ../archify/archify/bin/archify.mjs visual-check docs/diagrams/architecture.html --json --out-dir ../archify-evidence` checks the page in a real browser at four desktop sizes and writes its screenshots outside the repo.

  For the sequence diagram, run the same steps with type `sequence` and the `order-sequence` files; only `docs/architecture.md` embeds its SVG.

## Changing a workflow

1. Design the nodes and expressions against n8n's own node reference and real-world examples.
2. Edit the JSON in `workflows/` (fixed IDs and credential IDs come from `scripts/lib/manifest.ts`), then run `pnpm run build:workflows` to regenerate any Code node it touches.
3. Validate the workflow JSON with an n8n-aware validation tool until it reports no errors. It reports "typeVersion 2.8 exceeds maximum supported version 2.7" on a Postgres node; that's a known false positive to ignore, not a bug to fix — its node database stops at 2.7, and this repo pins Postgres nodes to 2.8 (see Conventions).
4. Run `pnpm run setup` to import and publish it against the local n8n instance. Add `-- --live` once the Shopify trigger's credential is ready — without it, `shopify-orders.json` stays unpublished (see Commands).
5. Run `pnpm run export` to write n8n's canonical form back to `workflows/` and regenerate Code nodes again. Commit that exported output, not your hand-edited JSON — the two can differ in server-assigned detail, and the exported form is what actually runs.
6. Run `pnpm run setup` and `pnpm run export` a second time, then `git diff --exit-code workflows/` — a clean diff confirms import and export stay idempotent; a non-empty one means a field is leaking the instance's own state into the committed JSON (extend `scripts/lib/normalize-workflow.ts`'s volatile-fields list).
7. Run the full gate below before committing.

A call made right after `pnpm run setup` restarts n8n can still run the previous published version for a few seconds: `/healthz` reports healthy well before the publication reconciler syncs `workflow_published_version` to the active version, which it does on its own schedule (10 s by default). `pnpm run setup` waits 15 s past `/healthz` for exactly this reason; after any other restart of the `n8n` container, wait the same before calling a workflow.

## The theme toolchain

The storefront runs Shopify's free Horizon theme (pinned commit, `scripts/lib/horizon.ts`'s `HORIZON`), plus whatever this repo overlays onto it. Nothing in `theme/` is pushed to a store on its own; `pnpm run theme:assemble` downloads Horizon, overlays this repo's files onto it, and applies a short list of anchored edits into Horizon's own files, producing a complete theme at `.theme-build/theme/`. `theme/README.md` is the fuller write-up of this model, kept next to the overlay it documents; the summary here is for anyone who hasn't opened it yet.

- **Overlay.** Every file under `theme/` (except `README.md`) is copied onto the downloaded base. A file new to Horizon is `added`; one that replaces a Horizon file is `modified`.
- **Insertions.** `scripts/lib/theme-insertions.ts`'s `INSERTIONS` list makes small, surgical edits to Horizon's own files that a whole-file overlay can't express: a line inserted before an exact anchor, a settings group appended once, or a section added once to a JSON template (keeping its leading `/* ... */` comment). Each insertion names the file and either an anchor that must appear in it exactly once, or a key that must not already exist; a mismatch throws `InsertionError` immediately, naming the file and anchor, instead of silently landing in the wrong place or duplicating. A touched file counts as `modified`.
- **Theme check's gate is `failing: 0`, not a fixed offense count.** `pnpm run theme:check` runs `@shopify/theme-check-node` against the assembled theme. An error (severity 0) anywhere is always failing. So is any offense — any severity — in a file this repo added or modified, since those are ours to fix. Everything else is Horizon's own baseline: `theme-check-node` loads the Liquid docs it checks against from `Shopify/theme-liquid-docs@main` at run time (with a bundled fallback), so an unmodified Horizon file's own warnings can read differently between runs with no change in this repo. The baseline count is printed for visibility, and recorded in `theme/README.md` as "at the time of writing," but never asserted — only `failing: 0` has to hold.
- `THEME_ENTRIES` and `INSERTIONS` hold the free-shipping bar's and the coffee finder's entries, which `theme/README.md` lists. A new storefront feature adds its own entries the same way.

## Conventions

- Node 24 (`"engines": { "node": ">=24" }`), ESM (`"type": "module"`). `tsconfig.json` runs `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, with `noEmit` — there is no build step. It also includes `DOM` and `DOM.Iterable` in `lib`, since `src/theme/**` type-checks against the browser.
- No `.js` or `.mjs` source files. Scripts are `scripts/*.ts`, run directly with `node scripts/<name>.ts` (Node's native type stripping; no `tsx`). Tests are Vitest files at `tests/**/*.test.ts`. The only JavaScript in the repo is generated: `theme/assets/*.js` and Code-node `jsCode`.
- CLIs call external programs with `execFile` or `spawn` and an argument array, never a shell string, and guard their entry point so tests can import their functions without side effects.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path.
- No Code node is hand-written: each is `export function run(input) { ... }` in `src/nodes/<name>.ts` — pure, no I/O, no clock — compiled by `pnpm run build:workflows`; `pnpm run check` rejects any Code node not listed in `scripts/lib/manifest.ts`'s `CODE_NODES`. Those sources use the ambient `DateTime` global (`src/globals.d.ts`) instead of importing Luxon, since the Code-node sandbox provides it but has neither `require` nor Node builtins, `fetch`, `window`, or `document`; ESLint enforces that in `src/nodes/**`. `src/theme/**` runs in the browser instead, so ESLint bans `process`, `Buffer`, and `require` there.
- n8n's Code-node Task Runner (`@n8n/task-runner`) runs generated `jsCode` after setting `Object.defineProperty = () => ({})`, a sandbox hardening measure. esbuild's own IIFE output attaches every named export through that same function, so without a fix every export would silently vanish and `__node.run` would come back `undefined` — see `scripts/build-workflows.ts`'s `hardenAgainstFrozenDefineProperty`, covered by a dedicated test that simulates the frozen sandbox (`tests/lib/code-node.ts`'s `runJsCode` freezes the same way). Don't remove it when touching the build, and don't upgrade `esbuild` past its exact pin in `package.json` without re-checking this patch still applies to its codegen.
- Every Postgres node is pinned to `typeVersion: 2.8` (checked against `2.45.6`'s source and enforced by a test over every file in `workflows/`): from 2.8, each `{{ }}` query-parameter expression binds exactly one value, where 2.5–2.7 would split a text value containing a comma into extra bind values — `order_number` is merchant-formatted text, so a custom order prefix with a comma in it would otherwise corrupt the bound parameters.
- No Execute Workflow node ever sets `retryOnFail: true` (enforced by the same cross-file test): a retry would repeat a sub-workflow's own side effects, such as a second Postgres row or a duplicate email.
- A Postgres query's SQL comments never contain `$n` (enforced by `pnpm run check`): n8n formats a query client-side before sending it, replacing every `$N` in the raw text — comments included, since it works on the text, not a parsed statement — so a bound value containing a newline can end a `--` comment and turn whatever follows into live SQL. Document a query parameter in the sticky note or a plain comment instead, never with its own `$n`.

## Guardrails

- Secrets live only in `.env` (gitignored) and n8n credentials — never in code, workflow JSON, or committed config. No script prints a secret or a token: `setup-credentials.ts` detects which credentials already exist in n8n from a CLI export, never a decrypted one, and only ever logs a credential's name and id, never its `data`. `shopify-token.ts` never prints the client secret, the authorization code, or the access token; its only output is the authorize URL, its prompts, and the final `Saved SHOPIFY_ACCESS_TOKEN (scopes: …; expires: …)` line, and an error message carries the HTTP status and Shopify's error code, never the request body.
- Test data: emails use `example.com`; phone numbers use the prefix `5700000000`; customer names are invented. Everything in the repo, including store content, theme defaults, emails, and sheet headers, is in English. No contact details anywhere.
- Database topology: role `$N8N_DB_USER` owns database `n8n`, role `$APP_DB_USER` owns database `app` and its tables, and neither can connect to the other's database (`REVOKE ALL ... FROM PUBLIC`). n8n's Postgres node connects through the `App DB` credential as `app_runtime` (`$APP_RUNTIME_DB_USER`), which has `SELECT, INSERT` on `orders` only: no DDL, no `TRUNCATE`, and no access to `n8n`. The Postgres superuser exists only to bootstrap roles in `db/init/` and to run `db-migrate`; neither it nor `$APP_DB_USER` is ever configured in the n8n container. See `docs/database.md`.
- n8n is pinned to `2.45.6`; never move to an unstable `3.x` tag before one is stable. Dependabot's automated updates for `n8nio/n8n` exclude minor and major bumps, because beta and stable releases share plain semver tags.
- The tunnel forwards only the Shopify Trigger's own fixed webhook path. Every other path, including other `/webhook/…` paths, returns 404. Through the public ngrok URL (deferred live check, since it needs a real tunnel): `/`, `/rest/login`, `/webhook-test/x`, `/webhook/dev/x`, and `//webhook/x` each return 404, and only the trigger's own path reaches n8n.
- **The dev harness** (`node scripts/dev-call.ts`, `scripts/lib/dev-client.ts`, workflow `dev-harness.json`) is **localhost-only**: it calls `${N8N_URL}/webhook/dev` directly and is gated by an `X-Dev-Token` header (credential `nbcCredDevToken1`, env `DEV_HARNESS_TOKEN`). It routes on the request's `target` field to a fixed sub-workflow by Execute Workflow call, with no retry (a retry would repeat a sub-workflow's side effects), and responds with its result. It is **never exposed through the ngrok tunnel** — `ngrok/traffic-policy.yml` forwards only the Shopify Trigger's own fixed path, so the harness has no public route by construction — and must be **unpublished before any production use**. `pnpm run setup` publishes it with the other sub-workflows, with or without `--live`, so unpublishing it is a manual step: the harness is a build-time and demo tool, not part of the live order path.
- **Calling `intake-order` through the dev harness always starts `process-order` too**, fire-and-forget (`Process order`'s `waitForSubWorkflow: false`), which reaches Google Sheets, Gmail, and the Shopify GraphQL API. `scripts/check-dev-response.ts` refuses to call `intake-order` at all — exiting 1, naming which credential — whenever a Google, Gmail, or Shopify credential already exists in n8n, derived from `scripts/lib/manifest.ts`'s `CREDENTIALS` by type (never a hand-picked id list), detected the same non-decrypted-export way `setup-credentials.ts` detects an existing credential. Before running `node scripts/dev-call.ts intake-order '<json>'` by hand on a developer's stack, check the same way: a stack wired to the owner's real accounts would otherwise append a real sheet row and send real emails from that second execution.
- `pnpm run setup` without `--live` leaves any `liveTrigger` workflow (`shopify-orders.json`) unpublished, deliberately: the local default never turns on live Shopify order intake by accident. Pass `--live` only when you mean to accept real orders.
- **Every `pnpm run setup -- --live` cycles the Shopify webhook subscription.** Importing `shopify-orders` unpublishes its trigger, which deletes the trigger's subscription in Shopify; publishing it and the restart that follows create the subscription again. Shopify sends nothing for an order placed while no subscription exists, so that order never arrives (traced in n8n 2.45.6's source; not yet seen live). Don't run `setup` while live orders are expected.
- Point tooling only at this repo's local n8n instance (`http://localhost:5678`), never another instance.
- **A missing or unparseable `config/config.json` also silences the error-workflow's own alert email**: `error-handler` loads config the same way every other workflow does (`load-config`, unvalidated), so if that read itself fails, there is no email to send. Each `error-handler` run then fails once and stops: `load-config` names no error workflow, so its own failure can't start another `error-handler` run (with one, a single failed call looped about 40 times a second while the file was missing). The only way to detect this case is n8n's own executions list (`error-handler`'s and the failing workflow's), not an inbox. Fix the file (`pnpm run check:config` validates it), then recover each order as in "Recovering an order that passed the gate and then failed" below.
- **`SHOPIFY_STORE` in `.env` and `config.shopify.store` must name the same store subdomain.** The Shopify credential (built from `.env` by `setup-credentials.ts`) and the config value read by workflows (validated by `validateConfig`) are two independent sources for the same fact; nothing cross-checks them, so a mismatch sends API calls to one store while the config describes another. This matters most for `process-order`'s "Read stock and brew methods": its endpoint is built from `config.shopify.store`, but the request authenticates with the Shopify credential built from `SHOPIFY_STORE` — a mismatch sends an authenticated request to the wrong store's `/admin/api/.../graphql.json`, which either 404s (and alerts the owner after retries) or, if that subdomain happens to exist and the credential is somehow valid there too, silently reads a different store's stock.
- **The stock check reads stock and brew methods through the GraphQL node, not HTTP Request.** Shopify returns a throttling error as an ordinary HTTP 200 response with a non-empty `errors` array, which HTTP Request's own retry logic — keyed on HTTP status — never sees as a failure worth retrying. The GraphQL node throws a `NodeApiError` whenever the response carries `errors`, so this workflow's standard `retryOnFail: true, maxTries: 3, waitBetweenTries: 1000` actually retries a throttled call instead of silently accepting the half-empty response. It also takes the query as its own string parameter, so the multi-line query needs no JSON-escaping inside a request body. The trade-off: the GraphQL node exposes no per-request timeout (see the README's Limitations).
- **"Wait before guide" survives an n8n restart, because the delay is long enough to persist.** n8n 2.45.6 only keeps a Wait node's sleep in the process's own memory when it's under `MAX_IN_PROCESS_WAIT_MS` (65 seconds); anything at or past that threshold is written to the database instead, and the leader's WaitTracker polls for due executions every 60 seconds and resumes them, restart or not. `config.guide_delay_minutes` is validated at 2 or more for exactly this reason: even a 1-minute wait (60 seconds) stays under that 65-second ceiling and would be silently lost on a restart, instead of resuming late.
- **The Orders sheet's tab title must match `config.google.orders_tab` exactly, and the sheet needs a header row whose names match the `OrderRow` keys**, in order: `date | order_number | customer | city | products | units | subtotal | shipping | total | free_shipping` (see `docs/shopify-setup.md`). `process-order`'s "Upsert order row" node resolves the tab by name (Google Sheets 4.7 ignores `columnToMatchOn`; a list or URL locator can't resolve a tab name from an expression, so it must stay in `name` mode) and auto-maps the sheet row's fields onto the header row's columns by name. Before writing, it compares the header row with the ten columns stored in the node, so a missing or misspelled header column fails the write with "Column names were updated after the node's setup", naming the missing columns; a renamed tab fails with "Sheet with name … not found".
- **The intake split.** A webhook-started execution can only call a *published* workflow, and `shopify-orders.json`'s own trigger (the Shopify credential) can't be published offline (see "A liveTrigger workflow" above). Splitting the order path into two workflows lets the whole chain run — and be tested — before a live Shopify store exists: `shopify-orders` holds only the credentialed trigger and a handoff; `intake-order` holds everything else (normalize, record, gate, load and check config, hand to `process-order`) behind a plain Execute Workflow Trigger, which publishes like any other sub-workflow. The dev harness's `intake-order` target exercises that same published chain directly, without a real signed order.
- **Shopify answers before the order is recorded.** The Shopify Trigger's `responseMode` is `onReceived`: n8n sends its HTTP 200 the moment the request is accepted, before `Hand to intake` or anything inside `intake-order` runs. A failure anywhere past that point (a database outage, a bad hand-edited config) never shows up as a non-200 response to Shopify — only in n8n's own executions list.
- **A request that fails the HMAC check gets HTTP 200 and starts no execution.** The Shopify Trigger computes the signature itself; a mismatch makes it return no workflow data, so nothing downstream ever runs, but n8n still answers the request with its normal `200 {"message":"Webhook call received"}` — there's no distinct failure response to watch for. A wrong or rotated `SHOPIFY_CLIENT_SECRET` therefore drops every order silently: Shopify sees success and never retries, and no execution reaches the error workflow. Recovery: put the app's current secret in `SHOPIFY_CLIENT_SECRET`; if the old secret was revoked, the offline token died with it, so run `pnpm run shopify:token` too. Then run `pnpm run setup -- --refresh nbcCredShopify01 --live`, compare Shopify's own delivery log for the topic against n8n's executions list for `shopify-orders` to find what was lost, and rebuild each lost order by hand: its sheet row, and its brewing guide if it has an email address.
- **Recovering an order stuck at the idempotency gate.** `intake-order`'s `Record order` step reports a bare `{success: true}` with no `order_id` in two different cases that look identical from the gate's side: a genuine duplicate (the order was already recorded), or a first INSERT that actually committed but whose response never reached n8n before a retry ran the same, now-conflicting statement. Tell them apart with `SELECT * FROM orders WHERE order_id = '<id>'`: if the row is there and this was a real, already-handled order, rebuild its downstream record (sheet row, emails) by hand instead of resending it — resending only re-triggers the gate, which stops it again. If it was a test order, delete that row and re-send it.
- **A failed order alerts twice.** `intake-order` and `shopify-orders` both carry `settings.errorWorkflow: nbcErrorHandler1`, so when `intake-order` fails, n8n runs the error workflow once for that failed sub-execution and again for its calling parent (`shopify-orders`, since `Hand to intake` waits on it and the sub-execution's failure fails the parent too) — the owner gets two emails naming two different executions for the same order, not two different orders.
- **Recovering an order that passed the gate and then failed** — for example, a bad value in `config/config.json` that fails `Check config`, or `process-order` being unavailable. Unlike a gate failure, the order is already recorded in `orders`, so simply re-sending it would stop at the gate instead of trying again:
  1. Fix the underlying cause (correct the config, make `process-order` available again).
  2. Delete that order's `orders` row.
  3. Retry the failed `shopify-orders` execution from n8n's executions list — not `intake-order`'s own, since retrying a sub-execution in place would replay whatever config it already loaded and stored, missing the fix just made. Retrying from `shopify-orders` instead starts a fresh `intake-order` call, which loads config again and now reaches the gate as a clean, new delivery.

## Supply-chain hardening

Package management is pnpm, pinned in `package.json`'s `packageManager` to an exact `11.x` version; never move to pnpm 12 (Dependabot's dependency-graph parser does not yet read its default two-document lockfile). `pnpm-workspace.yaml` holds the settings pnpm 11 no longer reads from `.npmrc`:

- `minimumReleaseAge: 4320` — refuses to install any package version (including transitive) published less than 3 days ago, so a newly-compromised release has a window to be caught and pulled before this repo can pull it in.
- `minimumReleaseAgeExclude: []` — pnpm 11 ships a default exclusion list for `n8n`/`n8n-*`/`@n8n/*`; this repo overrides it with an empty one, so no package is exempt from the age gate above.
- `trustPolicy: no-downgrade` — fails an install if a package's trust evidence (provenance/trusted publishing) regresses from an earlier release, or if the pinned pnpm version itself would downgrade that evidence.
- `blockExoticSubdeps: true` — only a direct dependency may resolve from a git or tarball URL; every transitive dependency must come from the registry.
- `strictDepBuilds: true` with `dangerouslyAllowAllBuilds: false` — a dependency's install/postinstall script fails the install unless it's explicitly approved in `allowBuilds`; nothing runs by silent default.
- `engineStrict: true` — a dependency whose `engines` range excludes this repo's Node fails the install instead of warning.
- `allowBuilds` lists only packages a real `pnpm install --frozen-lockfile` proved need their build script, each with a one-line reason. Check `esbuild: true` (its postinstall re-links the platform-specific `optionalDependencies` binary over the `bin/esbuild` JS shim) as the one-entry example — `@shopify/theme-check-node` and its dependencies carry no install-time script, so the theme toolchain needs no entry of its own; add another only after the same proof.

`tests/supply-chain.test.ts` reads these back through `pnpm config list --json` — pnpm's effective config, not the YAML text — so a misspelled key or a value pnpm silently ignores fails the test. It also asserts `packageManager`'s exact-pnpm-11 shape, that `package-lock.json` doesn't exist, that no tracked file still teaches an `npm` command, and that every Compose `image:` line carries a `@sha256:` digest.

**Updating a dependency:** edit `package.json`, run `pnpm install` (not `--frozen-lockfile`) to update `pnpm-lock.yaml`, run the gate below, and commit both files together. `minimumReleaseAge` will refuse a version published too recently — that's a feature, not a bug to work around; wait it out or pin an older compatible version.

**Landing a security fix younger than the 3-day gate:** a patched version sometimes ships less than 3 days before you need it in. To install it anyway:
1. Add a temporary entry to `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude`, scoped to that one package and version (pnpm accepts `name@version`, e.g. `"esbuild@0.28.3"` — not the bare package name, which would exempt every future version too), with a `#` comment naming the advisory ID and today's date.
2. Run `pnpm install` and merge as usual.
3. Remove the entry once that version is older than 3 days.

`tests/supply-chain.test.ts` asserts `minimumReleaseAgeExclude` is empty, so it goes red the moment step 1 lands — on purpose: the failing test is the reminder to do step 3. Let the test stay red for that one PR's lifetime rather than weakening the assertion for everyone; if that would make CI unmergeable, the simpler rule is to wait out the 3-day gate instead of landing it early, since this repo's own traffic rarely needs the override badly enough to justify a widened test.

**Images** (`compose.yaml`, `compose.queue.yaml`) are pinned `name:tag@sha256:<digest>`, the multi-arch index digest from `docker buildx imagetools inspect name:tag`, so the same reference resolves correctly on both arm64 (local) and amd64 (CI). Dependabot keeps an existing digest current as new builds of that tag are published, but won't add one that isn't there — a tag bump still needs the digest re-resolved the same way and the tag reviewed by hand first.

**CI** installs with `pnpm/setup` (pinned by commit SHA) then `actions/setup-node` with `cache: pnpm`, then `pnpm install --frozen-lockfile`, then `pnpm audit --audit-level=high`.

**The `n8n` job** (`.github/workflows/ci.yml`) is the one job that boots the real stack and proves a workflow executes — both the app Postgres path and two generated Code nodes — not just that the committed JSON is well-formed. It runs `node scripts/init-env.ts` (CI has no repo secrets, so `.env` is generated, not copied by hand) and `cp config/config.example.json config/config.json` — `Check config` accepts the example as-is, since it already satisfies `validateConfig` (a well-formed email, a non-empty sheet id and tab, a store subdomain and API-version pattern, both integer thresholds), so no CI-only edit to it is needed. No credential data ever touches the `.n8n-import/` bind mount (see that directory's own entry in Repo map above), so the job needs no CI-only permissions step for it — the runner's uid (1001) and n8n's own uid (1000) inside the container never need to read or write the same file there. It brings up only `postgres` and `n8n` (`--wait`), runs `pnpm run setup` (which migrates first), then `node scripts/check-db.ts` (the runtime role's denials, its exact grant, the one workflow statement, and the migration ledger), then `node scripts/check-dev-response.ts --fresh` — which refuses to run at all if a Google, Gmail, or Shopify credential somehow exists (it never does in CI), and `--fresh` means the `intake-order` check only accepts the fresh-call shape, never the duplicate-gate one, since CI's database starts empty every run — and tears down with `docker compose down -v` in an `if: always()` step, since CI's volumes are disposable, unlike a local stack's. What CI doesn't run, and why: `pnpm run send-test-order` and the `--live` Shopify trigger (needs a real Shopify store and credential); `process-order`'s Sheets, Gmail, and Shopify steps (same reason — no Google or Shopify credential in CI); and the queue-mode stack (`compose.queue.yaml`, which adds nothing `check-dev-response.ts` doesn't already prove).

**Dependabot** (`.github/dependabot.yml`) adds a 7-day cooldown to every ecosystem, beyond GitHub's own platform-wide default: `npm` (which also covers the pnpm lockfile) gets semver-tiered days (14 major, 7 minor, 7 patch); `docker-compose` and `github-actions` get a flat `default-days: 7`, since neither has a universal semver convention for "major/minor/patch". Dependabot waits 7 days before proposing a version update, so every version PR is already past pnpm's 3-day `minimumReleaseAge` install gate — it never arrives asking to install a version the gate would still refuse. Security updates are proposed immediately, cooldown-free, since Dependabot never delays those.

## Definition of done

- `pnpm run typecheck && pnpm run lint && pnpm test && pnpm run build:workflows -- --check && pnpm run check && pnpm run build:theme -- --check && pnpm run theme:check` all pass locally — run this full gate before every commit that touches TypeScript.
- No secrets anywhere in the diff or git history; `.env` and `config/config.json` are never committed.
- `README.md` (Status, What works now, and the quick start if commands changed) and this file are updated to match what the change actually adds.
- Commits follow Conventional Commits, on a branch named `task-NN-<slug>`.
