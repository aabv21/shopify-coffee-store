# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

This repo builds the order-processing backend for Nubandina Coffee, a fictional Shopify coffee store, as an n8n workflow backed by Postgres, plus the storefront theme. It is a portfolio demo: every file should read as production-quality, not a prototype.

## Repo map

- `compose.yaml`, `.env.example` — the local runtime: Postgres and n8n in Docker Compose, plus an optional ngrok tunnel (profile `tunnel`).
- `compose.queue.yaml` — an optional override that adds Redis and `n8n-worker` containers for queue mode; see Commands.
- `db/schema.sql`, `db/init/` — the application database schema (table `orders`) and the one-time role/database bootstrap script.
- `ngrok/traffic-policy.yml` — the tunnel's traffic policy: forwards only the Shopify Trigger's own fixed webhook path, denying every other path, including other webhook-shaped ones.
- `config/config.example.json` — the config template; a developer's own `config/config.json` is gitignored. `src/lib/config.ts` holds `validateConfig`, the pure validator both `scripts/check-config.ts` and `scripts/setup.ts` run against it — see Commands.
- `data/products.csv` — the Shopify product import CSV: 3 coffee origins (Nariño, Huila, Sierra Nevada) in 250 g and 500 g, with the `coffee` namespace metafields (roast, tasting notes, brew method). Header spelling and value formats (`Active`, `TRUE`/`FALSE`, `DENY`) come from Shopify's public sample CSV, not a store download — there is no store yet. `data/brewing-guides.json` — one brewing guide per brew method (pour-over, espresso, french press), mounted into n8n at `/files/data/brewing-guides.json` for the guide-email workflow a later task adds.
- `docs/shopify-setup.md` — the owner's step-by-step guide for creating the dev store and importing the catalog: metafield definitions, currency format, the CSV import, shipping rates, the test payment gateway, and the product image credits. Manual; nothing in this repo runs it.
- `workflows/` — the n8n workflow JSON, mounted read-only into n8n. In place: `load-config` (reads and returns `/files/config/config.json`, unvalidated, failing loudly instead of silently when it's missing), `error-handler` (the shared error workflow: loads config, emails the owner a plain-text alert — this also covers a trigger that fails at startup, such as a revoked credential, which carries no `execution` data), `dev-harness` (a token-protected, localhost-only webhook for calling a sub-workflow directly; see Commands), `shopify-orders` (the thin entry point: the Shopify Trigger itself, plus a handoff to `intake-order` — see "The intake split" below), `intake-order` (normalizes the order, records it once, and hands it to `process-order`), and `process-order` (the core order workflow, entered through its own Execute Workflow Trigger with the input contract `{ order: NormalizedOrder, config: Config }`: builds one flat sheet row, upserts it into the configured Orders tab keyed by order number, then emails the owner a plain-text summary; later tasks extend it after "Email owner" with the low-stock check and the brewing-guide email). More workflows land in later tasks.
- `scripts/lib/manifest.ts` — the single source of truth for fixed workflow/credential/code-node IDs (`WORKFLOWS`, `CREDENTIALS`, `CODE_NODES`, `TRIGGER_WEBHOOK_ID`); `scripts/lib/` also holds the workflow types, `normalizeWorkflow`, `listJsonFiles`, the Docker Compose and `.env` helpers (`compose.ts`), the `/healthz` poll (`health.ts`), and the dev-harness client (`dev-client.ts`).
- `scripts/check-workflows.ts`, `scripts/build-workflows.ts`, `scripts/export-workflows.ts`, `scripts/import-workflows.ts`, `scripts/setup-credentials.ts`, `scripts/setup.ts`, `scripts/dev-call.ts`, `scripts/send-test-order.ts` — the workflow tooling CLIs; see Commands below.
- `src/nodes/` — Code-node sources for workflows (added with the workflows that need them). `src/theme/` — pure TypeScript modules behind the storefront theme. `src/globals.d.ts` declares the ambient `DateTime` global the n8n Code-node sandbox provides.
- `tests/` — Vitest tests; `tests/setup.ts` provides the `DateTime` global at test time, matching the sandbox. `tests/lib/code-node.ts` runs a generated Code node's `jsCode` the way n8n's real Task Runner sandbox does (`Object.defineProperty` replaced with a no-op before the code runs). `tests/fixtures/workflows/` holds the hygiene-check fixtures: `clean.json` is a valid workflow, each other file is `clean.json` plus one defect. `tests/fixtures/orders/` holds raw `orders/create` payload fixtures (`tests/lib/orders.ts`'s `fx` loads them), covering a normal order, free shipping, a guest with no email or addresses, two shipping methods, and low stock.
- `tsconfig.json`, `eslint.config.ts`, `vitest.config.ts`, `package.json` — the TypeScript toolchain.
- `.n8n-import/` — created locally by the quick start; a scratch directory n8n's CLI reads credentials and workflows from. It's a live bind mount: never `rm -rf` it; the tooling only ever deletes the specific files it writes there.
- `.github/workflows/`, `.github/dependabot.yml` — CI (quality, security, actions lint jobs; CodeQL once the repo is public) and automated dependency updates.

## Commands

- `npm ci` — install dependencies from the lockfile.
- `npm run typecheck` — `tsc --noEmit`.
- `npm run lint` — `eslint .`.
- `npm test` — `vitest run`.
- `docker compose ls` — list running Compose stacks; run this before starting the stack, since every demo in this series binds `127.0.0.1:5678`. Stop any other demo's stack first.
- `docker compose up -d --wait` — start Postgres and n8n, and wait for both to report healthy.
- `docker compose --profile tunnel up -d --wait` — also start the ngrok tunnel (needs `NGROK_AUTHTOKEN` and `NGROK_DOMAIN`).
- `docker compose down` — stop the stack. Add `-v` to also drop the named volumes (destructive: wipes the database and n8n's data).
- `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` — switch to queue mode: adds Redis and the given number of `n8n-worker` containers, which run executions instead of the main process. `n8n-worker` extends `compose.yaml`'s own `n8n` service (same encryption key, database settings, and read-only `/files` mounts), with its published port reset so it scales past one replica without a conflict.
- `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — return to the regular, single-process stack. Plain `down`, with no `-v`, keeps the named volumes.
- `npm run build:workflows` — bundles each `src/nodes/*.ts` Code node with esbuild into its node's `jsCode`, and sets its `notes` to `Why Code: <why>`. Add `-- --check` to fail (exit 1) if the committed JSON doesn't match the source, without writing — that's what CI runs.
- `npm run check` — hygiene checks on every file in `workflows/`: pinned data, `meta.instanceId`, required settings, a literal email/phone/long-id/secret, an unknown credential id, a hand-written or undocumented Code node, an external-service node without the required retry, a Postgres query built from an expression instead of `$n` parameters, a Postgres query with a `$n` placeholder inside a SQL comment, and a missing sticky note. `node scripts/check-workflows.ts <dir>` runs it against any directory and prints `<file>: <message>` per violation.
- `npm run check:config` — runs `validateConfig` (`src/lib/config.ts`) against `config/config.json` and prints `config OK`, or the first validation error with a non-zero exit.
- `npm run setup` — validates `config/config.json` first (same check as `check:config`; stops before touching anything else if it fails), then imports credentials (`scripts/setup-credentials.ts`) and publishes workflows (`scripts/import-workflows.ts`) into the local n8n instance, in that order (`node scripts/setup.ts`, not `a && b`, so `-- --live`/`-- --refresh <id>` flags reach both steps). Skips a credential whose `.env` values are blank, or one that already exists unless named with `--refresh <id>` (any number of times) — re-importing a credential replaces it, which would otherwise drop an interactive Google sign-in. Skips a workflow not yet in `workflows/`. **A `liveTrigger` workflow (`shopify-orders.json` today) is only published with `--live`** — `npm run setup` on its own leaves the Shopify trigger unpublished, so running it again after a live publish (for example, to refresh a credential) takes the store's live order intake offline unless `--live` is passed again.
- `npm run export` — writes n8n's canonical form of every known workflow back to `workflows/` and regenerates their Code nodes; run this after editing a workflow in the n8n UI, and commit the result.
- `node scripts/dev-call.ts <target> '<json>'` — calls the dev-harness webhook (`POST {N8N_URL}/webhook/dev`) directly, for exercising a sub-workflow offline, without a real Shopify order. For example, `node scripts/dev-call.ts load-config '{}'` returns `{ "config": { ... } }` read straight from the mounted file. `node scripts/dev-call.ts intake-order "$(cat tests/fixtures/orders/below-threshold.json)"` runs the whole intake chain against a fixture order: the harness shapes the raw payload into one item the same way the Shopify Trigger would emit it, then calls `intake-order` directly, bypassing the HMAC check entirely (that's the point — it's for exercising the chain behind the trigger, not the trigger itself; `scripts/send-test-order.ts` drives the real, signed path). Needs `DEV_HARNESS_TOKEN` in `.env` (never printed). An unknown target answers 404. `load-config` and `intake-order` exist today; later tasks add more targets the same way. See Guardrails below for the harness's own workflow, `dev-harness.json`.
- `npm run shopify:token [-- --client-credentials]` — gets the Admin API access token for n8n's Shopify credential (`docs/shopify-setup.md` "Admin API access"). By default it runs Shopify's authorization code grant: it prints an authorize URL, reads the resulting callback URL from stdin, and exchanges the code for an offline token that doesn't expire. `--client-credentials` is the fallback for a same-organization dev store: a token that expires in 24 h, which then needs `npm run shopify:token -- --client-credentials` and `npm run setup -- --refresh nbcCredShopify01 --live` re-run daily (the `--live` matters; see `npm run setup` above). Either way it writes `SHOPIFY_ACCESS_TOKEN` into `.env`, keeping the file at mode 0600.
- `npm run send-test-order [-- --fixture <name>] [--order-id <digits>] [--tamper]` — signs a fixture order from `tests/fixtures/orders/` exactly as Shopify signs a real `orders/create` webhook (HMAC-SHA256 of the raw body, base64) and posts it to the local Shopify Trigger's real, fixed webhook path, reading `N8N_URL`, `SHOPIFY_STORE`, and `SHOPIFY_CLIENT_SECRET` from `.env` (never printed). `--fixture` defaults to `below-threshold`; `--order-id` defaults to the current timestamp. `--tamper` mutates the body after signing it, so the signature no longer matches — this drives the real, HMAC-checked entry point (`shopify-orders`), unlike the dev harness, which bypasses it. Needs `shopify-orders` published with `--live` to do anything useful; see "Live checks (pending)" in the README.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` CLI commands need no owner account, `--userId`, or `--projectId` (checked against `2.45.6`). `publish:workflow` only takes effect after an n8n restart; `npm run setup` restarts n8n itself, but only when it actually published something, then waits for `/healthz` and an extra 15 s (see "Changing a workflow" below).

## Changing a workflow

1. Design the nodes and expressions against n8n's own node reference and real-world examples.
2. Edit the JSON in `workflows/` (fixed IDs and credential IDs come from `scripts/lib/manifest.ts`), then run `npm run build:workflows` to regenerate any Code node it touches.
3. Validate the workflow JSON with an n8n-aware validation tool until it reports no errors. It reports "typeVersion 2.8 exceeds maximum supported version 2.7" on a Postgres node; that's a known false positive to ignore, not a bug to fix — its node database stops at 2.7, and this repo pins Postgres nodes to 2.8 (see Conventions).
4. Run `npm run setup` to import and publish it against the local n8n instance. Add `-- --live` once the Shopify trigger's credential is ready — without it, `shopify-orders.json` stays unpublished (see Commands).
5. Run `npm run export` to write n8n's canonical form back to `workflows/` and regenerate Code nodes again. Commit that exported output, not your hand-edited JSON — the two can differ in server-assigned detail, and the exported form is what actually runs.
6. Run `npm run setup` and `npm run export` a second time, then `git diff --exit-code workflows/` — a clean diff confirms import and export stay idempotent; a non-empty one means a field is leaking the instance's own state into the committed JSON (extend `scripts/lib/normalize-workflow.ts`'s volatile-fields list).
7. Run the full gate below before committing.

A call made right after `npm run setup` restarts n8n can still run the previous published version for a few seconds: `/healthz` reports healthy well before the publication reconciler syncs `workflow_published_version` to the active version, which it does on its own schedule (10 s by default). `npm run setup` waits 15 s past `/healthz` for exactly this reason; after any other restart of the `n8n` container, wait the same before calling a workflow.

## Conventions

- Node 24 (`"engines": { "node": ">=24" }`), ESM (`"type": "module"`). `tsconfig.json` runs `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, with `noEmit` — there is no build step. It also includes `DOM` and `DOM.Iterable` in `lib`, since `src/theme/**` type-checks against the browser.
- No `.js` or `.mjs` source files. Scripts are `scripts/*.ts`, run directly with `node scripts/<name>.ts` (Node's native type stripping; no `tsx`). Tests are Vitest files at `tests/**/*.test.ts`. The only JavaScript in the repo is generated: `theme/assets/*.js` and Code-node `jsCode`.
- CLIs call external programs with `execFile` or `spawn` and an argument array, never a shell string, and guard their entry point so tests can import their functions without side effects.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path.
- No Code node is hand-written: each is `export function run(input) { ... }` in `src/nodes/<name>.ts` — pure, no I/O, no clock — compiled by `npm run build:workflows`; `npm run check` rejects any Code node not listed in `scripts/lib/manifest.ts`'s `CODE_NODES`. Those sources use the ambient `DateTime` global (`src/globals.d.ts`) instead of importing Luxon, since the Code-node sandbox provides it but has neither `require` nor Node builtins, `fetch`, `window`, or `document`; ESLint enforces that in `src/nodes/**`. `src/theme/**` runs in the browser instead, so ESLint bans `process`, `Buffer`, and `require` there.
- n8n's Code-node Task Runner (`@n8n/task-runner`) runs generated `jsCode` after setting `Object.defineProperty = () => ({})`, a sandbox hardening measure. esbuild's own IIFE output attaches every named export through that same function, so without a fix every export would silently vanish and `__node.run` would come back `undefined` — see `scripts/build-workflows.ts`'s `hardenAgainstFrozenDefineProperty`, covered by a dedicated test that simulates the frozen sandbox (`tests/lib/code-node.ts`'s `runJsCode` freezes the same way). Don't remove it when touching the build, and don't upgrade `esbuild` past its exact pin in `package.json` without re-checking this patch still applies to its codegen.
- Local shell note: if `npm` is aliased to another package manager on your machine, run `command npm` to reach the real npm.
- Every Postgres node is pinned to `typeVersion: 2.8` (checked against `2.45.6`'s source and enforced by a test over every file in `workflows/`): from 2.8, each `{{ }}` query-parameter expression binds exactly one value, where 2.5–2.7 would split a text value containing a comma into extra bind values — `order_number` is merchant-formatted text, so a custom order prefix with a comma in it would otherwise corrupt the bound parameters.
- No Execute Workflow node ever sets `retryOnFail: true` (enforced by the same cross-file test): a retry would repeat a sub-workflow's own side effects, such as a second Postgres row or a duplicate email.
- A Postgres query's SQL comments never contain `$n` (enforced by `npm run check`): n8n formats a query client-side before sending it, replacing every `$N` in the raw text — comments included, since it works on the text, not a parsed statement — so a bound value containing a newline can end a `--` comment and turn whatever follows into live SQL. Document a query parameter in the sticky note or a plain comment instead, never with its own `$n`.

## Guardrails

- Secrets live only in `.env` (gitignored) and n8n credentials — never in code, workflow JSON, or committed config. No script prints a secret or a token: `setup-credentials.ts` detects which credentials already exist in n8n from a CLI export, never a decrypted one, and only ever logs a credential's name and id, never its `data`. `shopify-token.ts` never prints the client secret, the authorization code, or the access token; its only output is the authorize URL, its prompts, and the final `Saved SHOPIFY_ACCESS_TOKEN (scopes: …; expires: …)` line, and an error message carries the HTTP status and Shopify's error code, never the request body.
- Test data: emails use `example.com`; phone numbers use the prefix `5700000000`; customer names are invented. Everything in the repo, including store content, theme defaults, emails, and sheet headers, is in English. No contact details anywhere.
- Database topology: role `$N8N_DB_USER` owns database `n8n`, role `$APP_DB_USER` owns database `app`, and neither can connect to the other's database (`REVOKE ALL ... FROM PUBLIC`). The Postgres superuser exists only to bootstrap those roles in `db/init/`; it is never configured in the n8n container.
- n8n is pinned to `2.45.6`; never move to an unstable `3.x` tag before one is stable. Dependabot's automated updates for `n8nio/n8n` exclude minor and major bumps, because beta and stable releases share plain semver tags.
- The tunnel forwards only the Shopify Trigger's own fixed webhook path. Every other path, including other `/webhook/…` paths, returns 404. Through the public ngrok URL (deferred live check, since it needs a real tunnel): `/`, `/rest/login`, `/webhook-test/x`, `/webhook/dev/x`, and `//webhook/x` each return 404, and only the trigger's own path reaches n8n.
- **The dev harness** (`node scripts/dev-call.ts`, `scripts/lib/dev-client.ts`, workflow `dev-harness.json`) is **localhost-only**: it calls `${N8N_URL}/webhook/dev` directly and is gated by an `X-Dev-Token` header (credential `nbcCredDevToken1`, env `DEV_HARNESS_TOKEN`). It routes on the request's `target` field to a fixed sub-workflow by Execute Workflow call, with no retry (a retry would repeat a sub-workflow's side effects), and responds with its result. It is **never exposed through the ngrok tunnel** — `ngrok/traffic-policy.yml` forwards only the Shopify Trigger's own fixed path, so the harness has no public route by construction — and must stay **unpublished before any production use**. `npm run setup` without `--live` is exactly the state to leave it in day to day (see "Changing a workflow" above): the harness is a build-time and demo tool, not part of the live order path.
- `npm run setup` without `--live` leaves any `liveTrigger` workflow (`shopify-orders.json`) unpublished, deliberately: the local default never turns on live Shopify order intake by accident. Pass `--live` only when you mean to accept real orders.
- Point tooling only at this repo's local n8n instance (`http://localhost:5678`), never another instance.
- **A missing or unparseable `config/config.json` also silences the error-workflow's own alert email**: `error-handler` loads config the same way every other workflow does (`load-config`, unvalidated), so if that read itself fails, there is no email to send. The only way to detect this case is n8n's own executions list (`error-handler`'s and the failing workflow's), not an inbox.
- **`SHOPIFY_STORE` in `.env` and `config.shopify.store` must name the same store subdomain.** The Shopify credential (built from `.env` by `setup-credentials.ts`) and the config value read by workflows (validated by `validateConfig`) are two independent sources for the same fact; nothing cross-checks them, so a mismatch sends API calls to one store while the config describes another.
- **The Orders sheet's tab title must match `config.google.orders_tab` exactly, and the sheet needs a header row whose names match the `OrderRow` keys**, in order: `date | order_number | customer | city | products | units | subtotal | shipping | total | free_shipping` (see `docs/shopify-setup.md`). `process-order`'s "Upsert order row" node resolves the tab by name (Google Sheets 4.7 ignores `columnToMatchOn`; a list or URL locator can't resolve a tab name from an expression, so it must stay in `name` mode) and auto-maps the sheet row's fields onto whichever columns the header row already names — a missing or misspelled header column either fails the write or silently lands the value in the wrong column instead of the one its key names.
- **The intake split.** A webhook-started execution can only call a *published* workflow, and `shopify-orders.json`'s own trigger (the Shopify credential) can't be published offline (see "A liveTrigger workflow" above). Splitting the order path into two workflows lets the whole chain run — and be tested — before a live Shopify store exists: `shopify-orders` holds only the credentialed trigger and a handoff; `intake-order` holds everything else (normalize, record, gate, load and check config, hand to `process-order`) behind a plain Execute Workflow Trigger, which publishes like any other sub-workflow. The dev harness's `intake-order` target exercises that same published chain directly, without a real signed order.
- **Shopify answers before the order is recorded.** The Shopify Trigger's `responseMode` is `onReceived`: n8n sends its HTTP 200 the moment the request is accepted, before `Hand to intake` or anything inside `intake-order` runs. A failure anywhere past that point (a database outage, a bad hand-edited config) never shows up as a non-200 response to Shopify — only in n8n's own executions list.
- **A request that fails the HMAC check gets HTTP 200 and starts no execution.** The Shopify Trigger computes the signature itself; a mismatch makes it return no workflow data, so nothing downstream ever runs, but n8n still answers the request with its normal `200 {"message":"Webhook call received"}` — there's no distinct failure response to watch for. A wrong or rotated `SHOPIFY_CLIENT_SECRET` therefore drops every order silently: Shopify sees success and never retries, and no execution reaches the error workflow. Recovery: `npm run setup -- --refresh nbcCredShopify01 --live`, then compare Shopify's own delivery log for the topic against n8n's executions list for `shopify-orders` to find what was lost.
- **Recovering an order stuck at the idempotency gate.** `intake-order`'s `Record order` step reports a bare `{success: true}` with no `order_id` in two different cases that look identical from the gate's side: a genuine duplicate (the order was already recorded), or a first INSERT that actually committed but whose response never reached n8n before a retry ran the same, now-conflicting statement. Tell them apart with `SELECT * FROM orders WHERE order_id = '<id>'`: if the row is there and this was a real, already-handled order, rebuild its downstream record (sheet row, emails) by hand instead of resending it — resending only re-triggers the gate, which stops it again. If it was a test order, delete that row and re-send it.
- **A failed order alerts twice.** `intake-order` and `shopify-orders` both carry `settings.errorWorkflow: nbcErrorHandler1`, so when `intake-order` fails, n8n runs the error workflow once for that failed sub-execution and again for its calling parent (`shopify-orders`, since `Hand to intake` waits on it and the sub-execution's failure fails the parent too) — the owner gets two emails naming two different executions for the same order, not two different orders.
- **Recovering an order that passed the gate and then failed** — for example, a bad value in `config/config.json` that fails `Check config`, or `process-order` being unavailable. Unlike a gate failure, the order is already recorded in `orders`, so simply re-sending it would stop at the gate instead of trying again:
  1. Fix the underlying cause (correct the config, make `process-order` available again).
  2. Delete that order's `orders` row.
  3. Retry the failed `shopify-orders` execution from n8n's executions list — not `intake-order`'s own, since retrying a sub-execution in place would replay whatever config it already loaded and stored, missing the fix just made. Retrying from `shopify-orders` instead starts a fresh `intake-order` call, which loads config again and now reaches the gate as a clean, new delivery.

## Definition of done

- `npm run typecheck && npm run lint && npm test && npm run build:workflows -- --check && npm run check` all pass locally — run this full gate before every commit that touches TypeScript.
- No secrets anywhere in the diff or git history; `.env` and `config/config.json` are never committed.
- `README.md` (Status, What works now, and the quick start if commands changed) and this file are updated to match what the change actually adds.
- Commits follow Conventional Commits, on a branch named `task-NN-<slug>`.

## PR checklist

- [ ] The gate above passes.
- [ ] Test data uses `example.com` emails and the `5700000000` phone prefix; no real person's data.
- [ ] Docs reflect the change.
- [ ] The PR description states what was verified (commands and their output) and lists any deferred live checks.
